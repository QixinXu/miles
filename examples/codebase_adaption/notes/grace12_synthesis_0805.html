grace12 — full-run synthesis

Run smith-4b-v3nocurr-grace12 (ACT reward with CODEBASE_STEP_GRACE=12, otherwise identical to the gated arm). Consolidates seven analysis passes: early checkup (r0–63), memory-shortening analysis, three-era coverage audit (r8–62), close-reads of r74–78 and r90–97, ACT-quality audit r80–97, and the heldout-decline mechanism study. 2026-08-05, run position ≈ r97/191.

TL;DR

  • STEP_GRACE worked on its target and the effect held: none of the old collapse precursors (empty commands, multi-candidate blocks, length ratchet, pervasive hallucinated tokens) recurred through r97; same-metric blind-submit rate fell (12.1% → 4.1%); train success is at its run-high (46% at r95).
  • Memory shortsightedness was never fixed and has settled into a stable degenerate policy: per-rewrite wipes are now routine (37.9% of rewrites; 22.9% with no trigger at all), repo-switch wipes remain structural (80.5%), and final-memory coverage is flat at ≈1.75/12 issues — identical to the r74–78 valley.
  • A brand-new failure mode appeared at r88 and is ratcheting exponentially: "stall loops" — the model finishes (often correctly), announces completion, but never emits the submit token, burning the full 40-step budget on exit 0/echo done. Train-side: r88 first case → r95 5.7% → r96 7.3% → r97 18.2%. This is the most urgent live signal in the run.
  • The "heldout crash to 1/30" is mostly noise plus that new failure mode — and the scarier-looking 20→1 collapse I reported earlier was a units error on my side (see correction below). The real curve peaked at 6/30 and lives in a 2–5/30 noise band; r95's 1/30 got a direct push from 3 stall-loop trials landing on the only solvable instances.
  • Slow variable behind the low ceiling: verification depth collapsed (looked at test files before submitting: 80% → 30%; real verification pytest/repro: 44% → 22%) — the step-regret reward keeps paying for "guess a patch, fake-verify with python -c, submit fast".
Correction (my error, not the agents'): the heldout curve I had been reporting (10, 10, 3, 20, 17, …) mixed units — early points were success percentages, late points raw counts. The verified curve in solved-count/30 is: 3, 3, 1, 6 (r31 peak), 5, 3, 3, 4, 5, 2, 4, 1 (r95). Also note the heldout set is only 6 unique instances × 5 attempts, and 3 of the 6 have never been solved at any point — scores are essentially coin flips over 3 marginal instances. Read per-instance splits, not the headline number.

The stall loop, in one case

t10 THOUGHT: "The fix has been implemented and verified... wait_exponential_jitter now properly supports timedelta" CMD: echo "ALL DONE" t20–t39: exit 0 · exit 0 · exit 0 · ... (≈30 consecutive no-op turns) → Max steps (40) reached · eval_status=None · reward=0

The model knows it is done (thoughts stay coherent) but no longer retrieves the COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT action — a protocol-level forgetting. The single heldout pass at r95 came from a trial that drifted into the same "announce completion" groove and self-corrected one turn before budget death. Hypothesis to check in the reward code: submitting-and-failing and never-submitting may both earn reward 0, in which case "don't submit when unsure" is a regret-avoiding strategy RL can learn.

Interpretation: the WRITE policy has converged to "one-issue scratchpad, rewritten per issue". The apparent wipe-rate improvement (50%→38%) bought nothing — coverage is unchanged because what survives is boilerplate and current-issue text, not cross-issue knowledge. New memory-side pathologies (all first seen in r90–97)

  • repeat spam ep_1507 t11: two "Key file for debugging…" lines alternated 44+ times until token truncation — written after a reward=1 success, i.e. RL will reinforce it. One case now; watch it.
  • meta leakage 7/128 episodes copied the rewrite instruction itself into memory ("The task explicitly demands that I stop all current interactions and rewrite the memory…").
  • fabricated knowledge invented eval rules ("final output must contain only the three allowed sections" — no such rule), invented failure causes ("hidden binary file signature mismatch"), path-level drift (a function relocated to a file it never lived in).
  • sibling homogenization r97 group 194: three siblings' memories nearly identical — within-group variance (the GRPO signal source) is compressing.
  • memory–behavior dissociation a trial whose memory_in correctly warned "check that the replacement string exactly matches the target" then produced exactly that no-op-replace failure.

5. Synthesis: what the grace12 arm has proven

  • Proven (positive): pricing ACT steps with a 12-step grace window durably removed the efficiency-collapse precursors and improved train success — the ACT-side fix is real and stable for ~100 rollouts.
  • Proven (negative): next-trial-only WRITE pricing (gated_downstream) cannot maintain cross-issue memory, under any ACT regime — coverage sits at ~2/12 regardless. This is the direct motivation for the memwin3 arm (windowed Δ pricing, now running on babel) and the explore arm (judge penalizes wipes; queued as Slurm 129637).
  • New and unresolved: late-stage continual RL is now eroding protocol behaviors (submission token, memory-format adherence) and text integrity (garbling, repeat spam) — failure modes none of the earlier arms lived long enough to show. The stall-loop ratchet (18.2% at r97) will dominate both train and heldout numbers within ~10 rollouts if it continues.
  • Reward-design leads worth auditing now: (a) submit-and-fail vs never-submit may be reward-equivalent — if so, stalls are rational regret avoidance; (b) step-regret pressure demonstrably pays for skipping verification — grace12 softened the per-step penalty but the residual pressure still selects the fast-guess strategy on heldout-difficulty tasks.

7. Open decisions (for qixinx)

  • grace12 stop/continue: scientific conclusions are essentially complete (§5). Continuing mainly observes the stall-loop ratchet's endgame — which has some standalone value as a new-pathology natural experiment, but costs the node the queued explore arm is waiting for (129637 blocked on MaxNodePerAccount).
  • Submission-reward audit: quick code read of the reward for submit-fail vs never-submit; if equivalent, a small negative on never-submitting is a candidate fix for any future arm.
  • Heldout redesign: 6 instances × 5 attempts is too narrow; 3 instances are dead weight (never solved). Widen the set and report per-instance.
  • actonly ckpt offline evals: 16 ckpts (iter_7–127) on HF have never had post-hoc probe evals (the eval-iter47/119-style runs); needs a GPU slot and a task-set decision.
